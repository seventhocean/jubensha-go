# Baidu Tieba-inspired group system redesign

This change adds three new fields to the Group model (Banner, Notice, Rules), introduces a sticky topics API endpoint, and redesigns both the group detail page (with banner header, tab navigation, and sidebar) and the group list page (split into "My Groups", "Public Groups", and "Community Groups" sections). The migration uses GORM AutoMigrate and the frontend uses client-side fetching with a tabbed interface that lazy-loads pinned topics.

Watch for: The "Public Groups" section on the group list page will always be empty due to a data flow mismatch between backend filtering and frontend categorization (confirmed). The sticky topics endpoint returns unbounded results with no limit clause (confirmed). The "My Groups" section is also affected by the same backend filter — joined default groups won't appear (confirmed).

## High-level view

The backend adds three text/string fields to the Group model, a single new query method for sticky topics, and a standard migration. The new `/api/group/sticky_topics` endpoint mirrors the existing `GroupTopics` handler pattern but skips pagination entirely, relying on the assumption that sticky topics are rare.

The frontend group detail page is a complete rewrite with a rich banner header, three-tab layout (All Posts / Pinned / About), and a sidebar with announcements, rules, and member avatars. The tab switching lazy-loads pinned topics on first activation, avoiding unnecessary API calls.

The group list page splits the flat list into categorized sections, but the backend `GetPublicGroups()` service method filters to `is_default = 0`, meaning the API never returns groups where `isDefault = 1`. The frontend filters the response by `isDefault === 1` for the "Public Groups" section, producing an empty array every time. This section-splitting feature is broken without a backend query change.

4. **Redundant announcement/rules in About tab and sidebar** — The About tab renders announcement and rules unconditionally (with empty-state fallbacks), while the sidebar shows the same content when it exists. Groups with both fields set display duplicate information.

## Public Groups data flow mismatch

The `GetPublicGroups()` method in `group_service.go` applies these filters:

```go
Eq("status", constants.StatusOk).
Eq("visibility", 0).
Eq("is_default", 0).  // <-- excludes default groups
```

The `GroupList` handler passes these results directly to the frontend. In `groups._index.tsx`:

```typescript
const publicGroups = groups.filter((g) => g.isDefault === 1)
const communityGroups = groups.filter((g) => g.isDefault !== 1)
```

Since the API response never includes `isDefault = 1` groups, `publicGroups` is always empty. All groups land in "Community Groups". The "My Groups" section (filtering by `g.joined`) is similarly affected — users who joined default groups won't see them here.

The fix is either to remove the `is_default = 0` filter from `GetPublicGroups()` (letting the frontend separate them), or to create a new backend method that returns all visible groups including defaults.

## Unbounded sticky topics query

`GetGroupStickyTopics` does a `Find` with no `.Limit()`:

```go
sqls.DB().Where("group_id = ? AND sticky = ? AND status = ?", groupId, true, constants.StatusOk).
    Order("sticky_time desc").Find(&topics)
```

The existing `GetGroupTopics` method uses `Limit(limit + 1)` with cursor pagination. Adding a `.Limit(50)` or similar cap prevents runaway responses from moderator mistakes or bulk operations.

## Pinned tab loading inconsistency

The pinned topics tab shows a plain "Loading..." text string while fetching, whereas the prior UI/UX improvement PR introduced loading skeletons elsewhere in the app. This is a polish gap — the pattern should be a skeleton or at minimum a spinner component for visual consistency.
