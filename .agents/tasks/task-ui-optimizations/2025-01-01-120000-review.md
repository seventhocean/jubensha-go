# Groups UI optimizations: skeleton loading, sort/hot tabs, group creation, toast feedback

This change adds a batch of UX improvements to the groups feature across both frontend and backend. The frontend gains skeleton loading states, toast feedback on join/leave, a sort dropdown and hot tab for topics, client-side search, a create-group form, sticky topics in the "All Posts" tab, micro-animations, and mobile-friendly sidebar content in the About tab. The backend adds a hot topics endpoint (ordered by like_count + comment_count), sort parameter support on existing topics endpoint, and a POST endpoint for group creation with slug/name uniqueness checks.

Watch for: cursor-based pagination breaks under non-ID ordering in both hot topics and sorted topics endpoints (confirmed); slug has no format validation on the backend, allowing arbitrary strings including path-traversal-like values (confirmed); the `CreateGroup` member insertion error is silently dropped (confirmed).

## High-level view

The sort and hot topics endpoints use `id < cursor` filtering while ordering by non-ID columns. Once a user pages past the first batch, the cursor (an ID value) becomes meaningless against a `comment_count DESC` or computed-expression order — the second page will skip or duplicate rows depending on the data distribution. This is the most significant correctness issue in the change.

Group creation checks slug and name uniqueness at the application layer without a transaction wrapping the check-then-insert, though the database has unique indexes that will catch races. The slug field accepts any non-empty string with no regex or length validation, so a user could submit a slug with special characters, spaces, or reserved path segments (including "create", which would shadow the frontend route). The member-creation error after group insert is ignored, which could leave a group without its owner in the member table.

The `useEffect` in the group detail page that loads topics and sticky topics shares a dependency on `[group, sort]`, causing sticky topics and members to re-fetch unnecessarily on every sort change.

<summary>Issues (5)</summary>

1. **Cursor pagination breaks with non-ID sort orders** — `GetGroupTopics` with `most_replies` or `most_active` sort, and `GetGroupHotTopics`, all filter by `id < cursor` but order by a different column. Replace with offset-based pagination or a composite cursor that encodes the sort column value + ID.
2. **No slug format validation** — `CreateGroup` accepts any non-empty string as slug. Add a regex check (e.g., `^[a-z0-9]+(-[a-z0-9]+)*$`), length bounds, and a reserved-words blocklist (at minimum "create") in the backend handler.
3. **Owner member-insert error silently dropped** — `repositories.GroupMemberRepository.Create(sqls.DB(), member)` return value is not checked in `CreateGroup`. If this fails, the group exists without its owner as a member. Check the error and roll back or return it.
4. **Sticky topics re-fetch on sort change** — The `useEffect` in `groups.$slug.tsx` depends on `[group, sort]` but loads sticky topics (which don't depend on sort). Split the sticky-topic fetch into its own effect with `[group]` dependency only.
5. **Hot topics `hotLoaded` flag prevents refresh** — Once `hotLoaded` is true, switching sort or coming back to the hot tab never re-fetches. If topics are added, the tab stays stale for the session. Consider resetting `hotLoaded` on a meaningful trigger.

## Cursor pagination under non-ID ordering

`GetGroupHotTopics` orders by `(like_count + comment_count) DESC, id DESC` but paginates with `id < cursor`. Consider a group with topics: A (id=10, score=5), B (id=8, score=10), C (id=6, score=3). First page (limit 2) returns B, A in score order. Cursor becomes 10 (A's id). Second page filters `id < 10`, which excludes A but still includes B (id=8) — the results depend on which IDs happen to be below the cursor, not on score ordering.

The same issue applies to `GetGroupTopics` when `sort` is `most_replies` or `most_active`. The existing `latest` sort (ID desc) works correctly because the cursor and the ordering are aligned.

```go
// Current: broken for non-ID sorts
db = db.Where("id < ?", cursor)
db.Order("(like_count + comment_count) DESC, id DESC")
```

Fix options: (a) offset-based pagination for scored/sorted queries, (b) keyset pagination encoding `(score, id)` as a composite cursor, or (c) accept that "hot" is a fixed-rank view and only show a capped list without infinite scroll.

## Slug injection surface in group creation

The backend validates that slug is non-empty and unique, but performs no format validation:

```go
if body.Slug == "" {
    ginx.WriteJSON(ctx, ginx.ErrorMessage("slug is required"))
    return
}
```

A user can submit `"../admin"`, `"hot_topics"` (colliding with the API path segment, though Gin's route priority prevents actual shadowing), or unicode strings. The database column is `size:64` which provides length enforcement, but the application should reject slugs that don't match a URL-safe pattern before hitting the DB. The frontend `slugify` function sanitizes on the client side, but the backend is the trust boundary.

Additionally, a group with slug "create" would shadow the frontend route `/groups/create`. The client-side slugify function would produce "create" from the name "Create", so this isn't a contrived scenario.

## Silent member-creation failure in CreateGroup

```go
repositories.GroupMemberRepository.Create(sqls.DB(), member)
```

This return value is not checked. If the insert fails (constraint violation, connection issue), the group is persisted with `MemberCount: 1` but zero actual members. The owner would not appear in the members list and might not be able to leave (the `Leave` handler checks membership). Wrapping the group creation and member insertion in a transaction would be the robust fix, but at minimum checking and returning the error prevents silent inconsistency.

## Unnecessary sticky topic re-fetches

In `groups.$slug.tsx`, the effect that fetches topics, members, and sticky topics depends on `[group, sort]`:

```tsx
useEffect(() => {
  if (!group) return
  getGroupTopics(group.id, undefined, sort).then(...)
  getGroupMembers(group.id).then(...)
  getGroupStickyTopics(group.id).then(...)
}, [group, sort])
```

Sticky topics and members don't vary by sort. Every time the user changes the sort dropdown, three extra API calls fire for data that hasn't changed. Splitting into `[group]` for members/sticky and `[group, sort]` for topics eliminates the redundant requests.
