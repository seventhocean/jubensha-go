# Design system token overhaul and forum component CSS

This change replaces the existing oklch-based color system with a comprehensive hex-based design token layer derived from DESIGN.md. It introduces ~130 CSS custom properties covering brand colors, surfaces, ink, semantics, forum-specific indicators, motion, spacing, layout dimensions, and z-index. The header is updated to match the 52px sticky-header spec with backdrop-blur. A new `MobileBottomNav` component and a set of forum-specific CSS classes (topic items, comment threads, vote buttons, etc.) are added. Font loading for Inter and JetBrains Mono is wired through Google Fonts `<link>` tags.

Watch for: The mobile nav component is created but **never rendered** anywhere in the app (confirmed). The Tailwind v4 opacity modifier `bg-[var(--color-surface-1)]/95` in the mobile nav will silently fail because the variable resolves to a hex value, not a Tailwind-compatible color format (confirmed). Several forum CSS classes in topic.css have no consuming components yet, making them dead code until further work lands.

## High-level view

The token system is a 1:1 transcription of DESIGN.md into CSS custom properties, with a bridge layer that maps the new tokens back into shadcn/ui variable names (`--background`, `--primary`, etc.) so existing components continue working without modification.

The site header uses design system tokens for dimensions and visual treatment, with one notable choice: the background colors are hardcoded RGBA literals rather than referencing variables, which means custom-theme scenarios would require editing the component.

The mobile bottom nav is structurally complete but not mounted in the layout tree, producing no runtime effect. The body padding in common.css already accounts for it, which means mobile users get 56px of dead space at the bottom with no visible nav bar.

The forum component CSS classes in topic.css implement the DESIGN.md component specs but are not referenced by any React component. There's an unresolved architectural tension: the header and mobile nav use Tailwind utility classes directly, while topic.css defines BEM-style classes — no convention is established for which approach forum components should use.

The variables.css rewrite replaces old gradient-based body backgrounds with a theme-transition utility class, keyframe animations, and a reduced-motion media query. The old `--body-background` and `--topics-nav-color*` variables survive as legacy aliases mapped to new tokens, preventing breakage.

## MobileBottomNav wired but not mounted

No layout file imports or renders `<MobileBottomNav />`. Meanwhile, `common.css` already applies `padding-bottom: calc(56px + env(safe-area-inset-bottom, 0px))` on screens below 640px. Mobile users immediately see extra whitespace at the bottom of every page with nothing occupying it. Either the component should be mounted in the root layout (likely next to `<SiteHeader />`) or the body padding should be deferred until the component is actually rendered.

## Tailwind v4 opacity modifier on CSS variable backgrounds

In `mobile-bottom-nav.tsx`:

```
bg-[var(--color-surface-1)]/95
```

Tailwind's `/95` opacity modifier works by decomposing the color into channels and injecting an alpha. With hex values stored in CSS variables, Tailwind v4 cannot decompose them at build time — the variable is opaque to the compiler. The `/95` is silently dropped and the background renders at full opacity. Fix options: use an explicit `rgba()` literal (as the header does), store the token as an `rgba()` value, or use `color-mix(in srgb, var(--color-surface-1) 95%, transparent)`.

## Header background as inline RGBA

```
bg-[rgba(250,250,248,0.88)] dark:bg-[rgba(10,10,15,0.85)]
```

The color values `250,250,248` and `10,10,15` are the RGB equivalents of `--color-canvas` (`#fafaf8`) and dark canvas (`#0a0a0f`). If those tokens change, the header won't follow. A dedicated `--color-header-bg` token with alpha baked in would keep this in sync.

## Render-blocking external font stylesheet

The `<link>` stylesheet tag in root.tsx is render-blocking. The `display=swap` parameter ensures text remains visible during font load, but the stylesheet fetch itself still blocks rendering. For a forum where time-to-first-contentful-paint matters, consider `rel="preload" as="style"` with an `onload` handler, or self-hosting the font files.

## Utility-first vs. BEM-style class architectural tension

The header and mobile nav use Tailwind utility classes inline. The forum components in topic.css define BEM-style classes (`.forum-topic-item`, `.forum-vote-btn--active`, etc.). Once components are built, developers need to know which pattern to follow. These pre-defined classes can drift from actual usage if components end up using utilities directly — which is what the existing patterns in this very diff encourage.

## Breakpoint gap between nav and padding

The mobile nav uses `md:hidden` (Tailwind's 768px) while the body padding targets `max-width: 639px`. Screens between 640px and 767px will have no bottom padding and no nav bar once the component is mounted. If the nav should be visible on tablets below 768px, the padding should also cover that range.
