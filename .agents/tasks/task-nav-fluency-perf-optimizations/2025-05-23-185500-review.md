# Navigation fluency and perceived-performance optimizations

Three changes aimed at making the app feel faster without touching the server: link prefetch on hover, lazy-loaded images, and an optimistic follow button paired with `shouldRevalidate` guards on three routes. Together they eliminate visible loading spinners for same-page interactions and reduce initial payload by deferring offscreen images.

Watch for:
- `shouldRevalidate` returning `false` for same-pathname navigations suppresses reloads even when query-string changes carry meaningful state (confirmed).
- The optimistic follow button calls `onChanged?.(nextFollowed)` before the transition, propagating unconfirmed state to parent components immediately (confirmed).
- Avatars that appear above the fold on first paint (e.g., site header) will now request with `loading="lazy"`, potentially causing a visible pop-in (likely).

## High-level view

The prefetch plumbing adds a `prefetch` prop to `lib/router/link.tsx` with backward-compatible boolean coercion, flips the app-level default from `false` to `"intent"`, and adds explicit `prefetch="intent"` to the groups page's direct React Router Link usages. One ambiguity: `prefetch={false}` resolves to `undefined` (React Router's default) rather than `"none"`, which may surprise callers expecting explicit opt-out.

Image lazy loading is applied uniformly to avatars, topic images, article covers, comment images, and group cards. The blanket approach risks pop-in for above-the-fold avatars (site header, profile hero) that would benefit from an overridable `loading` prop defaulting to `"lazy"`.

The follow button's optimistic pattern toggles state before the API call, rolls back on failure, and reconciles against the server response. The `shouldRevalidate` guards on three routes prevent reloads when the pathname is unchanged, but ignore `searchParams`—any future query-param-driven filtering or pagination on those routes will silently skip revalidation.

1. **shouldRevalidate suppresses query-param-driven reloads** — The `currentUrl.pathname === nextUrl.pathname` guard returns `false` without checking `searchParams`. 3. **Optimistic state leaks to parent before confirmation** — `onChanged?.(nextFollowed)` fires before the API call. If a parent uses this callback to update a follower count, the user sees the effect of an unconfirmed action. Consider deferring `onChanged` until after the transition succeeds, or documenting that parents must handle rollback.
4. **Double state propagation on server mismatch** — If the server returns a `followed` value that differs from `nextFollowed`, `onChanged` fires a second time. Parents receive two callbacks for a single click (once optimistic, once corrective), which may cause flicker in derived UI like follower counts.

## shouldRevalidate and the query-string blind spot

The three `shouldRevalidate` exports share identical logic:

```tsx
if (currentUrl.pathname === nextUrl.pathname) {
  return false
}
return defaultShouldRevalidate
```

This targets tab-switch and hash-change scenarios within `TopicListRoute` and `UserProfileClientPage`, where sub-views are managed client-side and don't need fresh server data on every tab click.

The gap is that `URL.pathname` equality ignores `URL.search`. If a future feature encodes filter state, sort order, or cursor position in query params (a common pattern in paginated lists), the loader will not re-fire. The `_index.tsx` route currently uses a `LoadMore` component that fetches via client-side API calls rather than loader params, so the risk is latent today—but the guard is broader than necessary. A safer version would also compare `currentUrl.search === nextUrl.search` before suppressing revalidation.

## Optimistic follow with rollback

The follow button toggles state and fires `onChanged` before `startTransition` begins the API call. On failure, it rolls back both. On success, it reconciles against `result.followed`.

`onChanged` can fire up to three times for a single click in the worst case: once optimistic, once on rollback or mismatch. Parents that derive counts or trigger side effects from `onChanged` need to be idempotent or will flicker. The `pending` flag disables the button during the transition (preventing double-clicks), but the callback contract is now more complex than "called once with the final state."

## Blanket lazy loading on avatars

`UserAvatar` is the sole avatar component. It renders in the site header (visible on every page load), at the top of user profile pages, and in lists. Adding `loading="lazy"` unconditionally means the browser may defer fetching for avatars in the initial viewport. Modern browsers handle this heuristically—images close to the viewport top are often loaded eagerly despite the attribute—but the behavior varies across engines and is not guaranteed.

A pragmatic fix: accept a `loading` prop (defaulting to `"lazy"`) and pass `"eager"` from call-sites where the avatar is guaranteed above the fold (header, profile hero).

## Prefetch false-to-undefined mapping

`prefetch={false}` in the router-level component resolves to `undefined`, which means React Router uses its built-in default behavior (no prefetch). Anyone reading the code may expect `false` to map to `"none"` (the explicit opt-out value). A comment or mapping `false` to `"none"` would reduce ambiguity, especially since the app-level wrapper already changed the default to `"intent"`—call-sites passing `prefetch={false}` may intend a hard opt-out rather than "fall back to framework default."
